# 1. Purpose

This document defines the core data model of EduMind.

The purpose of this document is to establish a unified understanding of all business entities used throughout the system.

This document describes:

* Core entities
* Entity responsibilities
* Relationships between entities
* Data lifecycle

This document does **not** define database implementation details.

---

# 2. Data Model Overview

EduMind revolves around one central entity:

```text
Student
```

All other entities exist to support the student's learning journey.

The overall relationship is shown below.

```text
Student
│
├── StudentProfile
│
├── LearningPlan
│
├── LearningHistory
│
├── ChatSession
│
└── LearningResource
```

---

# 3. Core Entities

## 3.1 Student

Purpose

Represents the identity of a learner.

Responsibilities

* Basic user information
* Login identity
* Learning ownership

Suggested Attributes

* Student ID
* Name
* Grade
* Subject
* Target Score
* Created Time

Rules

Student does not store learning status.

Learning status belongs to StudentProfile.

---

## 3.2 StudentProfile

Purpose

Represents the current learning state of the student.

StudentProfile is the Single Source of Truth (SSOT) for all learning-related status.

Responsibilities

* Knowledge mastery
* Current learning objective
* Learning preferences
* Current recommendation
* Learning progress

Suggested Attributes

* Profile ID
* Student ID
* Current Goal
* Mastery Map
* Learning Preferences
* Last Recommendation
* Last Updated Time

Rules

Only StudentProfile stores the current learning state.

Other modules must never maintain independent copies of student status.

---

## 3.3 LearningPlan

Purpose

Represents the recommended learning path generated by the system.

Responsibilities

* Learning objectives
* Learning sequence
* Completion status

Suggested Attributes

* Plan ID
* Student ID
* Target Topic
* Learning Steps
* Recommendation Reason
* Status
* Created Time

Rules

LearningPlan records recommendations.

It does not record actual learning behavior.

---

## 3.4 LearningHistory

Purpose

Records the student's completed learning activities.

Responsibilities

* Learning history
* Assessment history
* Study duration
* Progress tracking

Suggested Attributes

* History ID
* Student ID
* Activity Type
* Topic
* Duration
* Result
* Timestamp

Rules

LearningHistory is immutable.

Historical records should never be modified.

---

## 3.5 ChatSession

Purpose

Represents one AI tutoring conversation.

Responsibilities

* Conversation history
* Learning questions
* AI responses

Suggested Attributes

* Session ID
* Student ID
* Conversation Summary
* Created Time
* Updated Time

Rules

ChatSession stores dialogue records.

It does not store learning status.

---

## 3.6 LearningResource

Purpose

Represents educational materials used by the RAG system.

Responsibilities

* Curriculum documents
* Textbook content
* Practice materials
* Reference resources

Suggested Attributes

* Resource ID
* Title
* Subject
* Topic
* Source
* Embedding ID

Rules

LearningResource contains only educational knowledge.

It never stores student information.

---

# 4. Entity Relationships

```text
Student
│
├── 1 StudentProfile
│
├── N LearningPlan
│
├── N LearningHistory
│
├── N ChatSession
│
└── N LearningResource (Referenced)
```

Relationship Description

Student owns exactly one StudentProfile.

Student may have multiple LearningPlans.

Student may have multiple LearningHistory records.

Student may have multiple ChatSessions.

LearningResource is shared across all students.

---

# 5. Data Lifecycle

## Persistent Data

The following entities must be permanently stored.

* Student
* StudentProfile
* LearningPlan
* LearningHistory
* ChatSession
* LearningResource

Persistent data survives system restart.

---

## Temporary Data

The following data exists only during request execution.

Examples

* RAG Retrieval Result
* Prompt Context
* LLM Intermediate Response
* Recommendation Cache
* API Request Context

Temporary data should never be written directly into persistent storage unless explicitly required.

---

# 6. Data Ownership

Every entity has exactly one owner.

| Entity           | Owner Module          |
| ---------------- | --------------------- |
| Student          | Student Profile       |
| StudentProfile   | Student Profile       |
| LearningPlan     | Recommendation Engine |
| LearningHistory  | Student Profile       |
| ChatSession      | LLM Service           |
| LearningResource | RAG Module            |

Ownership Rules

Only the owner module may modify its entity.

Other modules may read data through approved interfaces but must never modify it directly.

---

# 7. Data Consistency Rules

The following consistency rules are mandatory.

Rule 1

StudentProfile is the only source of current learning state.

Rule 2

LearningHistory records completed events only.

Rule 3

LearningPlan records future recommendations only.

Rule 4

ChatSession stores conversation records only.

Rule 5

LearningResource remains independent of student data.

Rule 6

Temporary execution data must never overwrite persistent entities.

---

# 8. Future Expansion

Future versions may introduce additional entities.

Examples

* Assignment
* ExamResult
* KnowledgeGraph
* Teacher
* Classroom
* Report

New entities must extend the existing model without modifying current entity responsibilities.

---

# 9. Summary

The EduMind data model is centered around one learner and one learning state.

Core Principle

Student

↓

StudentProfile

↓

Learning Process

↓

Learning Records

↓

Continuous Optimization

This structure ensures a stable, scalable, and maintainable foundation for future development.
